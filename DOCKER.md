# Running CSCMaster on Linux with Docker (PostgreSQL)

Three containers, started together by `docker-compose.yml`:

| Container | What it is |
|---|---|
| `cscmaster-postgres` | PostgreSQL 18 (free). Data in a Docker volume; port `POSTGRES_HOST_PORT` (default 5435) on 127.0.0.1 only. |
| `cscmaster-api` | The Web API (.NET 10), on server port `API_HOST_PORT` (default 8084) |
| `cscmaster-ui` | The web UI (.NET 10), on server port `UI_HOST_PORT` (default 8085) |

HTTPS and the domains are handled by the server's **main Caddy** (`rexl-api-backend`), which proxies to the UI and
the API (see "Main Caddy" below). The browser loads the UI from `UI_PUBLIC_URL` and calls the API directly at
`API_PUBLIC_URL`, so both need a public address.

**How updates flow:** push to the `postgres-migration` branch → GitHub Actions builds two images and publishes
`ghcr.io/retinuesoft/cscmaster-api` and `ghcr.io/retinuesoft/cscmaster-ui` (tags `latest` and `sha-<commit>`) →
on the server, `./update.sh` downloads the latest deployment files, applies database migrations, pulls the images
and restarts. The server needs no git clone and never builds code.

## 1. Prepare the server (once)

- Install Docker Engine with the compose plugin (https://docs.docker.com/engine/install/).
- Point both domains' DNS **A records** at the server's public IP (the main Caddy serves them).
- Do not open ports 8084/8085 to the internet: only the main Caddy needs them.
- Put a GitHub token in `/root/.github_token` (the same file the other RetinueSoft sites use; skip if it is already there). Token:
  GitHub → Settings → Developer settings → Personal access tokens → **Tokens (classic)**, scopes `repo` and `read:packages`:
  ```bash
  echo '<token>' | sudo tee /root/.github_token >/dev/null && sudo chmod 600 /root/.github_token
  ```
- Log the server's Docker in to ghcr.io once (as root, because update.sh runs with sudo; skip if already done for
  another site with a token that can read RetinueSoft packages). `update.sh` uses this login to pull the images:
  ```bash
  sudo cat /root/.github_token | sudo docker login ghcr.io -u <github-username> --password-stdin
  ```

## 2. Install

Only `update.sh` is downloaded by hand; it fetches the rest (repository and branch are fixed in the script).

```bash
mkdir -p ~/cscmaster && cd ~/cscmaster
sudo curl -fsSL -H "Authorization: Bearer $(sudo cat /root/.github_token)" -H "Accept: application/vnd.github.raw" \
  "https://api.github.com/repos/RetinueSoft/CSCMaster/contents/deploy/update.sh?ref=postgres-migration" -o update.sh
sudo chmod +x update.sh
sudo ./update.sh            # first run: downloads the files next to update.sh and creates .env, then stops
sudo nano .env              # fill in POSTGRES_PASSWORD; check UI_PUBLIC_URL, API_PUBLIC_URL and the ports
sudo ./update.sh            # second run: creates JWT_KEY, pulls the images, creates the tables, starts everything
```

`JWT_KEY` (the key that signs logins) is generated by `update.sh` when it is empty. Keep it: changing it logs
everyone out.

**Dates and time zones:** the server can be in any country. `BUSINESS_TIME_ZONE` (default `Asia/Kolkata`) decides
"today" and the report and petty-cash dates. The enrolment upload time is stored in UTC. `TZ` only affects log
timestamps. See "Dates" in DATABASE.md.

Folder on the server:

```
~/cscmaster/
├── .env                 your settings and passwords (created by update.sh, never downloaded)
├── docker-compose.yml   downloaded by update.sh
├── .env.example         downloaded by update.sh (template; new settings are copied into .env)
├── update.sh            the only file you download yourself; it keeps itself up to date
├── backup-db.sh         downloaded by update.sh
├── restore-db.sh        downloaded by update.sh
├── import-sqlserver.sh  downloaded by update.sh
└── backups/             database backups
```

## 3. Load the data from SQL Server

After the first install the tables hold only the built-in seed data. Load the data from the old SQL Server in one
of two ways. Both empty the PostgreSQL tables first, copy everything, convert the enrolment upload times to UTC,
move the id counters past the copied rows, and must end with **"Row counts match for all tables."**
Both can be re-run any time (each run starts from scratch).

### A. On the server, from a SQL Server backup (recommended)

1. On the Windows server, back up the database (SSMS → Tasks → Back Up, or
   `BACKUP DATABASE [CSCMaster] TO DISK = N'C:\Temp\CSCMaster.bak' WITH COPY_ONLY, INIT`).
   A `.bak` that holds several backups (SSMS appends by default) is fine: the newest full backup is used.
2. Copy it into the `backups` folder on the server, e.g. from the Windows machine:
   ```powershell
   scp C:\Temp\CSCMaster.bak <user>@<server-ip>:~/cscmaster/backups/
   ```
3. On the server:
   ```bash
   cd ~/cscmaster
   sudo ./import-sqlserver.sh backups/CSCMaster.bak
   ```
   It starts a temporary SQL Server container, restores the backup into it, runs the copy tool (included in the
   API image), restarts the API and UI and removes the temporary SQL Server. Needs about 2 GB of free memory.
   Delete the `.bak` afterwards if you no longer need it.

### B. From a Windows PC that can reach the old SQL Server

1. Open an SSH tunnel to the server's PostgreSQL (leave the window open):
   ```powershell
   ssh -N -L 15435:127.0.0.1:5435 <user>@<server-ip>
   ```
2. In the repository folder on the PC:
   ```powershell
   dotnet run --project tools/CSCMasterDataCopy -- "Server=<sql server>;Database=CSCMaster;Integrated Security=True;Encrypt=false;TrustServerCertificate=true" "Host=127.0.0.1;Port=15435;Database=cscmaster;Username=postgres;Password=<POSTGRES_PASSWORD>"
   ```

For the final switch: stop the old site on the Windows server, run the copy one last time, then point users to the
new site.

## Day-to-day

| Task | Command |
|---|---|
| Update to the newest version | `sudo ./update.sh` |
| Roll back to an earlier build | `sudo ./update.sh sha-1a2b3c4` (tags: GitHub → repository → Packages); `sudo ./update.sh` returns to latest |
| Restart | `docker compose restart api ui` |
| Logs | `docker compose logs -f api ui` |
| Stop everything | `docker compose down` (data is kept in Docker volumes) |
| Back up now | `sudo ./backup-db.sh` |
| Restore a backup | `sudo ./restore-db.sh backups/<file>.dump` (replaces the database) |
| Connect with pgAdmin/DBeaver | SSH tunnel `ssh -N -L 15435:127.0.0.1:5435 <user>@<server>`, then `localhost:15435`, user `postgres` |
| Update PostgreSQL itself | `docker compose pull postgres && docker compose up -d postgres` (back up first; minor 18.x updates only) |

What `update.sh` does each run: downloads `docker-compose.yml`, `.env.example` and the backup/restore/import
scripts (updating itself first), adds new settings to `.env` without changing your values, installs azcopy if it is
missing, pulls the images, applies new database migrations, and restarts what changed. Edit `docker-compose.yml`
in the repository, not on the server: `update.sh` replaces the server copy with the one from GitHub.

## Main Caddy

Add two site blocks to the main Caddy's Caddyfile (`rexl-api-backend`) and reload it:

```caddy
cscmaster.online {
    encode zstd gzip
    reverse_proxy localhost:8085
}

api.cscmaster.online {
    encode zstd gzip
    request_body {
        max_size 50MB          # enrolment CSV/ZIP uploads
    }
    reverse_proxy localhost:8084
}
```

The domains must match `UI_PUBLIC_URL` and `API_PUBLIC_URL` in `.env` (the API only accepts browser calls from
`UI_PUBLIC_URL`).

If that Caddy itself runs in a Docker container, `localhost` is the container, not the server: use
`host.docker.internal:8085` (add `extra_hosts: ["host.docker.internal:host-gateway"]` to its service)
or the server's Docker bridge address, `172.17.0.1:8085` (same for 8084).

## Scheduled backups to Azure

`backup-db.sh` dumps the database to `./backups` (`pg_dump`, compressed), uploads it to Azure Blob Storage with
`azcopy`, deletes the local file, and logs to `backups/backup.log`.

1. azcopy: `update.sh` installs it into `/usr/local/bin` when it is missing (x86-64 and ARM).
2. Put the container SAS URL in `.env` (single quotes; a plain `%3D`, not the `%%3D` used in `.bat` files):
   `AZURE_BACKUP_SAS_URL='https://<account>.blob.core.windows.net/<container>?sp=cw&...&sig=...%3D'`
3. Test: `sudo ./backup-db.sh; echo "exit code $?"; tail -n 8 backups/backup.log`
   (0 = OK, 1 = backup failed, 2 = upload failed and the local file is kept)
4. Schedule in root's crontab (`sudo crontab -e`), e.g. four times a day:
   ```cron
   0 2,9,13,18 * * * /home/<user>/cscmaster/backup-db.sh
   ```
   Cron uses the server's time zone: check with `timedatectl`.

## Notes

- The database schema comes from the EF Core migrations in `CSCMasterAPI/Migrations/Postgres`; `update.sh` applies
  new ones automatically (the API image contains a migration bundle, `efbundle`).
- `docker compose build` builds both images locally (for testing without GitHub).
