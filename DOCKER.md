# Running CSCMaster on Linux with Docker (PostgreSQL)

Three containers, started together by `docker-compose.yml`:

| Container | What it is |
|---|---|
| `cscmaster-postgres` | PostgreSQL 18 (free). Data in a Docker volume; port `POSTGRES_HOST_PORT` (default 5435) on 127.0.0.1 only. |
| `cscmaster-api` | The Web API (.NET 10), on port `API_HOST_PORT` (default 18084) on 127.0.0.1 only; public `https://<server-ip>:8084` |
| `cscmaster-ui` | The web UI (.NET 10), on port `UI_HOST_PORT` (default 8085) on 127.0.0.1 only |

The server is set up by **RetinueSoft/VpsSetup** (`/root/common`): one Caddy for HTTPS and the domains
(`caddy/sites/cscmaster.caddy`: `cscmaster.online` → UI, `https://<server-ip>:8084` → API), one GitHub token,
database backups to Azure, and the settings file `/root/common/env/cscmaster.env`. The browser loads the UI from
`UI_PUBLIC_URL` and calls the API directly at `API_PUBLIC_URL`, so both need a public address.

**How updates flow:** merge a `feature/...` branch into `release` → GitHub Actions builds
`ghcr.io/retinuesoft/cscmaster-api` and `ghcr.io/retinuesoft/cscmaster-ui` (tags `latest` and `sha-<commit>`) →
on the server, `sudo /root/cscmaster/update.sh` downloads the deployment files, pulls the images, applies database
migrations and restarts. The server needs no git clone and never builds code.

## Install (once)

`/root/common/setup.sh` installs every app listed in VpsSetup's `apps.conf`: it creates `/root/cscmaster` and
`/root/common/env/cscmaster.env` (check `UI_PUBLIC_URL`, `BUSINESS_TIME_ZONE`; `API_PUBLIC_URL` becomes
`https://<server-ip>:8084`) and starts it. The database password is `POSTGRES_PASSWORD` in `/root/common/.env`,
shared by all apps. To start it by hand: `sudo /root/cscmaster/update.sh`.

`JWT_KEY` (the key that signs logins) is generated by `update.sh` when it is empty. Keep it: changing it logs
everyone out.

**Dates and time zones:** the server can be in any country. `BUSINESS_TIME_ZONE` (default `Asia/Kolkata`) decides
"today" and the report and petty-cash dates. The enrolment upload time is stored in UTC. `TZ` only affects log
timestamps. See "Dates" in DATABASE.md.

Folders on the server:

```
/root/cscmaster/
├── update.sh            keeps itself up to date from the release branch
├── docker-compose.yml   downloaded by update.sh
├── .env.example         downloaded by update.sh (template; new settings are copied into the settings file)
├── .env                 generated from /root/common/.env + /root/common/env/cscmaster.env (do not edit)
├── import-sqlserver.sh  downloaded by update.sh (one-time data load, below)
├── backups/             SQL Server .bak files for import-sqlserver.sh
└── .deployed_sha        commit of the running images
```

## Load the data from SQL Server

After the first install the tables hold only the built-in seed data. Load the data from the old SQL Server in one
of two ways. Both empty the PostgreSQL tables first, copy everything, convert the enrolment upload times to UTC,
move the id counters past the copied rows, and must end with **"Row counts match for all tables."**
Both can be re-run any time (each run starts from scratch).

### A. On the server, from a SQL Server backup (recommended)

1. On the Windows server, back up the database (SSMS → Tasks → Back Up, or
   `BACKUP DATABASE [CSCMaster] TO DISK = N'C:\Temp\CSCMaster.bak' WITH COPY_ONLY, INIT`).
   A `.bak` that holds several backups (SSMS appends by default) is fine: the newest full backup is used.
2. Copy it into the `backups` folder on the server, e.g. from the Windows machine:
   ```powershell
   scp C:\Temp\CSCMaster.bak root@<server-ip>:/root/cscmaster/backups/
   ```
3. On the server:
   ```bash
   cd /root/cscmaster
   sudo ./import-sqlserver.sh backups/CSCMaster.bak
   ```
   It starts a temporary SQL Server container, restores the backup into it, runs the copy tool (included in the
   API image), restarts the API and UI and removes the temporary SQL Server. Needs about 2 GB of free memory.
   Delete the `.bak` afterwards if you no longer need it.

### B. From a Windows PC that can reach the old SQL Server

1. Open an SSH tunnel to the server's PostgreSQL (leave the window open):
   ```powershell
   ssh -N -L 15435:127.0.0.1:5435 root@<server-ip>
   ```
2. In the repository folder on the PC:
   ```powershell
   dotnet run --project tools/CSCMasterDataCopy -- "Server=<sql server>;Database=CSCMaster;Integrated Security=True;Encrypt=false;TrustServerCertificate=true" "Host=127.0.0.1;Port=15435;Database=cscmaster;Username=postgres;Password=<POSTGRES_PASSWORD>"
   ```

For the final switch: stop the old site on the Windows server, run the copy one last time, then point users to the
new site.

## Day-to-day

| Task | Command |
|---|---|
| Update to the newest version | `sudo /root/cscmaster/update.sh` |
| Back up first, then update | `sudo /root/cscmaster/update.sh --backup` |
| Roll back to an earlier build | `sudo /root/cscmaster/update.sh sha-1a2b3c4` (tags: GitHub → repository → Packages); `update.sh` without a tag returns to latest |
| Change a setting | `sudo nano /root/common/env/cscmaster.env`, then `sudo /root/cscmaster/update.sh` |
| Logs | `cd /root/cscmaster && docker compose logs -f api ui` |
| Stop everything | `cd /root/cscmaster && docker compose down` (data is kept in Docker volumes) |
| Back up now | `sudo /root/common/backup-db.sh cscmaster` |
| Restore a backup | `sudo /root/common/restore-db.sh cscmaster <file>` (replaces the database) |
| Connect with pgAdmin/DBeaver | SSH tunnel `ssh -N -L 15432:127.0.0.1:5435 root@<server>`, then `localhost:15432`, user `postgres` |

Edit `docker-compose.yml` in the repository, not on the server: `update.sh` replaces the server copy with the one
from the release branch.

**Domains / HTTPS:** `caddy/sites/cscmaster.caddy` in RetinueSoft/VpsSetup. **Backups:** `backup-db.sh` in VpsSetup
runs from `/etc/cron.d/retinuesoft` (02:00, 09:00, 13:00, 18:00 server time) and uploads to Azure
(`AZURE_BACKUP_SAS_URL` in `/root/common/.env`).

## Notes

- The database schema comes from the EF Core migrations in `CSCMasterAPI/Migrations/Postgres`; `update.sh` applies
  new ones automatically (the API image contains a migration bundle, `efbundle`).
- `docker compose build` builds both images locally (for testing without GitHub).
